The repository is a multi-language workspace glued together by three layers:

- Python entrypoint: `pyproject.toml` installs the `cortex_harness` package and exposes the `dev` command (`cortex_harness.dev:cli`). The `Makefile`, `dev.sh`, `dev.bat`, `dev.ps1` and `dev-global.cmd` are thin shims that delegate to either `scripts/mcp-lifecycle.py` (Unix) or `scripts/mcp-lifecycle.ps1` (Windows), which in turn call into `cortex_harness/dev.py`. That file is the single source of truth for every subcommand (`init`, `build`, `sync`, `start`, `stop`, `doctor`, `install`, `uninstall`) and owns the runtime wiring between children.
- Child orchestration: `dev.py` holds the canonical maps `LANG_ANALYZERS`, `FRAMEWORK_ANALYZERS`, `DOC_EXTENSIONS`, `MCP_SERVICES`, `_SCAFFOLD_DIRS`/`_SCAFFOLD_FILES`, and `_SCAN_EXCLUDE`. It discovers child modules by path (`CODE_TINY = REPO_ROOT / "code-tiny"`, `DOC_TINY = REPO_ROOT / "doc-tiny"`, `HARNESS_SCRIPTS = REPO_ROOT / "harness" / "scripts"`) and launches them as subprocesses with provider-neutral flags (`--graph-provider falkordb|neo4j`, `--qdrant-url`, `--collection`).
- Shared persistence contract: both `code-tiny` and `doc-tiny` write graph data to Neo4j/FalkorDB and vectors to Qdrant; the root CLI mediates environment translation (`_code_env_for_process`, `_doc_env_for_process`, `_env_to_neo4j_args`) so each child reads only its own namespace while sharing the same database endpoints. Per-project state lives under `.cortext-harness/config/*.json` (active env selection) and `.cortext-harness/sync-state/*.json` (git-commit + mtime/hash change tracking).
- Windows build surface: `cortex-harness.sln` groups the VB Roslyn worker (`code-tiny/tools/vb/roslyn_worker/RoslynVbWorker.csproj`) alongside solution folders, letting Visual Studio build the C# analyzer worker that the Python analyzers invoke.
- Installers & harness: `installers/` builds platform context menus using shared config read by the same lifecycle script; `harness/` provides the agent-session template and bash runner invoked from `dev run`.
- Tests, docs, plans: `tests/` exercises every analyzer against shared fixture projects; `docs/` and `plans/` are reference material consumed by the scaffolded project layout.
