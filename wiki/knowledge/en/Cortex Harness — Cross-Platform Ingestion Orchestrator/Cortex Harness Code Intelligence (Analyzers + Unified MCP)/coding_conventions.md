- Each primary analyzer exposes a CLI via `python -m tools.<lang>.<lang>_analyzer` accepting the portable argument set (`--root`, `--project-id`, `--language`, `--graph-provider`, `--qdrant-url`, `--embed-model`, etc.) documented in the README table.
- Framework overlay modules follow a fixed internal layout of `detector.py` + `pipeline.py` + `resolver.py` (+ optional `models.py`/`cache.py`) and write only graph facts, never vectors.
- Capability profiles are declared as `FrameworkQueryConfig` dataclasses in `mcp/framework_registry.py` with canonical name, aliases, labels, relationships, searchable properties, support dimensions, and features — all validated at import time by `validate_capability_registry`.
- MCP tool wrappers use the `_register_payload_tool` decorator pattern: a uniform parameter list is coerced into a merged dict and forwarded to `_dispatch_tool`, which resolves the active backend via `capability_for_parser(parser_type)` before dispatching `tool_<name>` on the selected module.
- Graph persistence goes through `tools.graph.core.factory.GraphDriverFactory.create_driver`, which inspects the URI scheme to transparently select `FalkorDBDriver` over `Neo4jDriver` when a FalkorDB-compatible scheme is detected.
- Environment configuration is centralized: harness configs are injected via `tools.common.harness_config.load_harness_config`, and runtime defaults are read from `os.environ` keys such as `NEO4J_*`, `FALKORDB_*`, `QDRANT_URL`, `CODE_EMBEDDING_MODEL`, and `EMBED_DEVICE`.
