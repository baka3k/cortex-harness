Two cooperating sub-packages under `harness/`:

- `scripts/` — executable entry points. `orchestrator.py` is the single CLI driver: it loads `.harness/config.yaml`, picks a `todo` or explicit task from `.harness/state/feature_list.json`, marks it `in_progress`, then executes the lifecycle in order: `init.sh` (env/MCP reachability probe), `context_selector.py` (builds per-session JSON context via two MCP servers), an optional user-supplied `--agent-command`, and finally `verify.sh`. Each phase is wrapped in try/except; failures set the task to `blocked` and write a `SessionLog` dataclass instance as JSON into `.harness/state/session_log/<session_id>.json`, while also appending human-readable lines to `.harness/state/progress.md`. Configuration is read through a custom `load_simple_yaml` + `cfg_get` helper so no third-party YAML dependency is needed.
- `templates/` — static scaffolding copied into a new project's `.harness/` directory: `config.yaml` (harness mode, MCP endpoints, budget caps, verify/supplemental commands, policy tool allowlists), `feature_template.json` / `session_template.json` (schema for the feature list and per-session log), `state/feature_list.json` (initial empty feature array), `AGENT.md` / `session-handoff.md` / `progress.md` (human-facing docs consumed by the agent), and `.claude/settings.json` for IDE integration.

Dependency direction is strictly one-way: `orchestrator.py` → `init.sh` / `context_selector.py` / `verify.sh`; `context_selector.py` has no import of orchestrator code. Both Python scripts are self-contained CLIs invoked via `subprocess.run` from the orchestrator, keeping the runtime boundary at process boundaries rather than module imports. The MCP client (`MCPHttpClient`) talks to `graph_mcp_url` and `mind_mcp_url` over plain HTTP POST using the jsonrpc 2.0 protocol with SSE support, and the fallback path retries ranked queries against the same mind endpoint when the first call yields no vector refs.
