# Repository findings — single-channel JSON MCP response contract (v2.0)

Research date: 2026-10-13. All paths absolute-repo-relative unless prefixed `.venv/` (installed lib evidence).
Legend: (verified) = read directly; (inferred) = deduced, marked where uncertain.

## Findings

### 1. Where CallToolResult is assembled — central choke points, not per-tool

- **graph_mcp (:8788, entry `code-tiny/mcp/unified_mcp.py`)** — ONE central middleware:
  - `mcp_server.middleware.append(_proxy_middleware)` at `code-tiny/mcp/unified_mcp.py:1163`; `_ProxyMiddleware.on_call_tool` at `:1039-1054` routes proxied tools through `_dispatch_tool`/`_dispatch_planner_tool` and wraps EVERY result (proxied and direct) via `_wrap_dispatch_result` (`:1054` else-branch).
  - `_wrap_dispatch_result` at `code-tiny/mcp/unified_mcp.py:984-1037`: builds `ToolResult(content=result_summary(...), structured_content=envelope, meta=result_meta(tool_name), is_error=...)` (success `:1031-1037`, error `:1018-1027`). It accepts either a raw dict payload or an already-built `ToolResult` (unwraps content text via `json.loads` at `:1009-1013`).
  - Final wire `CallToolResult` is produced by fastmcp **4.0.4** (`.venv/lib/python3.12/site-packages/fastmcp-4.0.4.dist-info/METADATA`; `requirements.txt:17` pins unpinned `fastmcp`): `ToolResult.to_mcp_result()` at `.venv/.../fastmcp/tools/base.py:171-190` — because `meta` is always set, it returns `CallToolResult(structured_content=..., content=..., is_error=..., _meta=...)`.
  - **SUPPRESSION POINT = the `structured_content=` argument in `_wrap_dispatch_result`** (one line each for success/error). Verified: with `structured_content=None` and `meta` set, `to_mcp_result` still returns a `CallToolResult`, and outgoing JSON-RPC serialization uses `model_dump(by_alias=True, mode="json", exclude_none=True)` (`.venv/.../mcp/shared/peer.py:57`) — so `structuredContent` is **absent from the wire, not null** (repro: `mcp_types.CallToolResult(..., structured_content=None).model_dump_json(exclude_none=True)` → field omitted). `isError` still round-trips because `to_mcp_result` forces `CallToolResult` when `meta`/`is_error` set (`base.py:181-187`).
  - Framework auto-generation exists but is bypassed: fastmcp `Tool.convert_result` (`.venv/.../fastmcp/tools/base.py:367-434`) would auto-embed dicts into `structuredContent` when `output_schema is None` (`base.py:422-426`) — this only fires if the middleware did NOT wrap. The middleware is load-bearing; removing/short-circuiting it would resurrect two-channel output for dict-returning tools.
- **mind_mcp (:8789, entry `doc-tiny/mcp_graph_rag.py`)** — ONE decorator, not middleware: `_standard_tool` at `doc-tiny/mcp_graph_rag.py:1371-1423` builds raw `mcp.types.CallToolResult` with `content=[TextContent(result_summary(...))]`, `structuredContent=envelope`, `isError`, `_meta=result_meta(...)` (success `:1397-1408`, error `:1380-1395`). Suppression = drop `structuredContent=` there.
- **Error middleware (separate path)**: `code-tiny/mcp/tool_error_middleware.py:55-112` returns `ToolResult(content=json.dumps(payload), structured_content=payload, is_error=True)` (note: **no `meta`** on this path). Installed ONLY on the standalone fast server (`code-tiny/mcp/fastmcp_server.py:2772`, `_install_global_tool_error_wrapper` `:2756-2780`); NOT installed in `unified_mcp.py` (grep verified) — unified catches tool exceptions inside `_dispatch_*` and returns `_build_tool_error` dicts (`unified_mcp.py:815-848`) which `_wrap_dispatch_result` normalizes.
- **Standalone fast server bypass (latent)**: `code-tiny/mcp/fastmcp_server.py` registers ~25 tools with `@mcp_server.tool` returning RAW dicts (e.g. `tool_list_databases` `:1122-1126`) with no envelope middleware; if run directly it defaults to port 8788 (`fastmcp_server.py:2824`) and would emit non-envelope responses (fastmcp auto structuredContent of the dict). dev.py launches `unified_mcp.py`, not this file (`cortex_harness/dev.py:199-204`), and `code-tiny/mcp/Readme.md:17` says "The normal entry point is unified_mcp.py". (verified bypass exists; inferred low traffic)

### 2. Current envelope shape (v1.0)

- `normalize_success` `cortex_harness/mcp_contract.py:51-54` → `{"ok": True, "data": data, "error": None}` (data by reference, no copy).
- `normalize_error` `:168-220` → `{"ok": False, "data": None, "error": {"code", "message", "retryable": bool, "details": dict}}`; code canonicalization `:16-22,45-48`, exception mapping `:57-79`, details sanitization allowlist `:27-42,86-93`, legacy-payload compaction `:96-165`.
- `result_meta` `:223-230` → `{"contract": "cortex.mcp.tool-result", "contractVersion": "1.0", "tool": name}` — placed in `_meta`, never in the payload.
- `result_summary` `:233-259` → success: `"Success: N results. Read structuredContent.data."` (counts `results|passages|items|ids`) or `"Success. Read structuredContent.data."`; error: the error message, else `"Tool execution failed. See structuredContent.error."`.
- **Real example** (normative spec, `docs/mcp-output-contract.md:43-77`): success with `content[0].text = "Success: 1 result. Read structuredContent.data."`, `structuredContent = {"ok": true, "data": {"db": "procsample", "results": [...], "ids": [...]}, "error": null}`, `isError: false`, `_meta` = the triple above. Empty variant `:92-116`; error variant `:123-150`.
- **Uniformity**: uniform for all 39 graph tools (middleware wraps everything, including the string-returning `list_mcp_functions` — its JSON string is parsed then enveloped, `unified_mcp.py:1574-1580` + `:1009-1013`) and all 5 mind tools (decorator). NOT uniform on the standalone fast server path (finding 1). Fan-out merged payloads (`_FANOUT_*` sets `unified_mcp.py:154-220`) are enveloped like any other dict.

### 4. Choke point for JSON-into-content + size cap

- Best choke point graph: inside `_wrap_dispatch_result` (`unified_mcp.py:984-1037`) — it already owns payload→envelope→ToolResult; serialize envelope once there (`json.dumps(envelope, ensure_ascii=False)`; `ToolResult(content=str)` is auto-converted to one TextContent by `_convert_to_content`, `fastmcp/tools/base.py:126`). mind: same inside `_standard_tool` (`mcp_graph_rag.py:1371-1423`). Error middleware `tool_error_middleware.py:108-112` only matters for standalone fast server.
- **Existing size-cap utilities: none shared.** Searches for `max_size|MAX_*|truncate|truncat` found only: (a) fastmcp's `ResponseLimitingMiddleware` (`.venv/.../fastmcp/server/middleware/response_limiting.py`) — byte-cap + suffix truncation of TEXT; it would cut mid-JSON, NOT reusable as-is for a never-break-JSON cap (verified reading its `_truncate_to_result` docstring/logic); (b) per-tool `max_passage_chars` blunt `text[:n]` cut on mind semantic tools (`mcp_graph_rag.py:1503,1542-1543,1586,1682-1683`); (c) `SCOPE_MAX_TARGETS` fan-out cap (doc-tiny scope, default 12, test fixture `tests/test_semantic_graph_scope_block.py:85`); (d) `seeds_truncated` flag `code-tiny/mcp/semantic_graph_expansion.py:150`. A new structural truncation helper (drop/trim `data` content, set `truncation` field, keep JSON parseable) must be written — nothing to reuse directly.

### 6. Error path today and single-channel shape

- `normalize_error` output: `{ok: false, data: null, error: {code, message, retryable, details}}` (`mcp_contract.py:211-220`). Legacy `_build_tool_error` payloads (`unified_mcp.py:815-848`: `type`, `tool`, `query_engine`, param catalogs, `example`, `next_step`) are compacted by `_compact_legacy_details` (`mcp_contract.py:96-165`) into small `details`.
- Content stub on error = `envelope["error"]["message"]` (`unified_mcp.py:1021-1023`; `mcp_graph_rag.py:1385-1389`) — i.e. today the human-readable message is duplicated in content.
- Single-channel: keep `isError=true` (semantics unchanged, set from `ok is False` at `unified_mcp.py:1003-1005,1026`) and put the SAME error envelope JSON in `content[0].text`. testtool impact: `mcp_client.call_tool` sees non-empty text → raises `MCPError(raw-JSON-string)` (`mcp_client.py:144-149`); recommended client tweak: parse the JSON first and raise `MCPError(envelope["error"]["message"] or raw JSON)` so error text stays human-readable. Protocol-level failures (unknown tool, malformed JSON-RPC) stay JSON-RPC errors, never the tool envelope (`docs/mcp-output-contract.md:170-171`; client `_unwrap` `mcp_client.py:85-92` raises on `error` key). `tests/test_mcp_testtool_client.py:31-51` pins the current raise behavior.

### 10. Risks / open questions

- **Wire field absence (verified)**: `structured_content=None` → field omitted on the wire (`exclude_none`, `mcp/shared/peer.py:57` + repro). But note `isError` path also emits `resultType: "complete"` unconditionally (mcp_types 2.2.0 repro output) — new-ish field clients may notice; harmless (inferred).

## Recommended approaches

1. Put the single-channel serializer + structural size cap inside `_wrap_dispatch_result` (`unified_mcp.py:984-1037`) and `_standard_tool` (`mcp_graph_rag.py:1371-1423`) — the two existing envelope choke points — with shared helpers (`serialize_envelope`, `cap_envelope`) added to `cortex_harness/mcp_contract.py` so both servers and the standalone fast server share them; pass `structured_content=None` (wire field then disappears, verified).
2. Migrate consumers in one change set: invert `mcp_client.call_tool` to content-first (parse JSON, isError-first, raise with `error.message`), rewrite `mcp_batch_report.validate_contract`/`classify_response` to parse `content[0].text` and replace the 1000-char rule with a cap-conformance check, then update the 5 contract test files (finding 5 rows 4-9).
3. Version as v2.0: bump `MCP_CONTRACT_VERSION` + `CONTRACT_VERSION`, rewrite `docs/mcp-output-contract.md` channel semantics (keep error-code table), update `mcp-batch-report-guide.md`, and run the documented live smoke on both 8788 and 8789.
