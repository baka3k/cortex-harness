# Red team review — 260924-1642-yake-dynamic-rules-doc-sync

Reviewed: 2026-09-24, against working tree of `/Users/hieplq1.aip/AI/cortex-harness` (plan.md, phase-01..04, research-digest.md). All refs verified by reading code; key claims re-executed (venv import checks, `uv pip install --dry-run`, CliRunner invocation).

## Verdict

**FIX-FIRST.** The plan's line references and env-flow claims are largely accurate (rare for this repo), but the design has 3 correctness-level holes (missing spaCy model in the effective venv, empty-pattern rule files crashing the shared rules dir, cross-project prune destruction) and one broken E2E command form. Do not start Phase 02 until C1–C3 are re-decided.

## Critical (must fix before implementation)

- **C1 — `en_core_web_sm` is NOT installed in the effective venv; the headline feature silently no-ops.** Effective interpreter is repo `.venv` (`_venv_python`, cortex_harness/dev.py:1403-1416; `doc-tiny/.venv` absent). Verified: `.venv/bin/python -c "import spacy.util; spacy.util.is_package('en_core_web_sm')"` → `False` (spacy 3.8.16 present). Phase-02 §3 builds `nlp_ruler = build_spacy_pipeline(args.spacy_model=...)` guarded try/except → warn + `None` on the default config. So "GLiNER tiêu thụ rules" (plan.md output 2) will not happen out of the box; Phase-02 test 3's `skipUnless` would permanently skip; Phase-04 E2E checkbox (b) fails. No phase installs the model. Fix: add install step + pin (or use `spacy.blank("en")` + entity_ruler — lighter, no download, and also fixes M2).
- **C2 — Empty `{"patterns": []}` rule files poison the shared rules dir.** Phase-01 §1 specifies `generate_for_file` returns `{"patterns": []}` for empty text and `write_rule_file` writes it. But `build_spacy_pipeline.load_patterns` **raises** `ValueError("EntityRuler JSON has no patterns")` on an empty list (doc-tiny/entity_extractors.py:156-157) and the dir path loads every `*.json` (164-171). Consequences: one scan-quality PDF (YAKE yields 0 keywords after dedup/min-length) → (a) gliner path: entire ruler merge silently disabled for the whole run (guarded), (b) spacy provider: `build_spacy_pipeline` at graphrag_ingest_langextract.py:1277 and :715 is **unguarded** → folder full sync crashes. Fix in plan: never write empty rule files (delete stale file instead), and/or relax the validator; add a test for the empty-pattern path.
- **C3 — Global `doc-tiny/rules/` + per-run prune = cross-project rule destruction and stem collisions.** `--yake-rules-dir` defaults to repo-level `doc-tiny/rules` for every project synced through this harness. Folder-mode prune keeps only `keep_sources` of the current run (phase-02 §2), so project A's `sync doc all` **deletes project B's** `ruler.from-yake.*` files; B's next extraction then loads only A's rules (rules-dir merge). Also `source_key = stem sanitized` collides: folder-mode `source_id` is relpath-based (`_safe_source_id`, graphrag_ingest_langextract.py:644-646 → `a__spec.pdf` vs `b__spec.pdf`) but the rule file name is stem-only → `docs/a/spec.pdf` and `docs/b/spec.pdf` (and `spec.pdf` vs `spec.txt`) clobber each other; last writer wins, extraction of the other runs with wrong rules. plan.md D2's "tránh cross-project clobber" claim is defeated by its own naming scheme. Fix: scope to `rules/from-yake/<project_id>/<safe_source_id>.json` (keyed like `_safe_source_id`), or move prune/lifecycle entirely to dev.py which knows `deleted_rel`.

## Major (should fix)

- **M1 — Prune is unreachable for deleted docs in normal operation.** Incremental mode spawns one subprocess per *changed* file only (dev.py:1285-1295); a deletion-only run spawns **zero** subprocesses (state hashes popped at dev.py:1312-1313, then return). Interactive `sync doc` uses `force_mode="auto"` (dev.py:3675) and has no `--full` flag, so folder mode (= the only prune site) never re-runs after the baseline exists; only `sync doc all` (force full, dev.py:3729) prunes. Meanwhile orphan rule files remain **active** in `effective_ruler` (dir merge) and pollute every later extraction. Phase-04 step 4 half-acknowledges ("hoặc ghi chú nếu chỉ prune ở full") — that is not a mitigation. Fix: dev.py deletes rule file(s) for `deleted_rel` directly.
- **M2 — `ruler_match` returns spaCy NER output, not ruler matches.** `build_spacy_pipeline` = `en_core_web_sm` + entity_ruler (entity_extractors.py:135-141); `nlp(text).ents` therefore includes the statistical NER's PERSON/ORG/GPE/... entities. Per phase-02 §4 these all get `confidence: 1.0` and beat GLiNER on `(name.casefold(), type)` collisions — the plan claims only high-precision "ruler" wins (D3). Additionally `ruler.overwrite_ents = False` (entity_extractors.py:141) means ruler labels lose to NER labels on overlapping spans *inside* the sidecar pipeline, so even the label-heuristics precedence is not real. Fix: ruler-only sidecar (`spacy.blank("en")` + ruler) or filter ents by ruler provenance.
- **M3 — D1's rationale is contradicted by the actual design (PDF parsed twice).** D1: "chạy YAKE ngay tại chỗ tránh parse PDF 2 lần". Phase-02 §2 pre-pass calls `yake_rules.generate_for_file(path)` whose `load_text` re-parses the PDF (phase-01 §1), then main's `_read_input_text`/`read_pdf_text` parses it again (graphrag_ingest_langextract.py:1286, 1304, ...). Either pass the already-read `raw_text` into the pre-pass, or drop the D1 claim.
- **M4 — `effective_ruler = args.ruler_json or rules-dir` precedence bug.** If a user passes `--ruler-json <file>` on the gliner path, the freshly generated yake files (and the static dir) are silently dropped from the merge — opposite of the feature's goal; it must be union (ruler_json ∪ rules dir). Related: spacy provider is explicitly left unchanged (phase-02 §5 "giữ nguyên"), so plan.md D2's "static + động cùng load" does not hold for provider=spacy, and Phase-04's documented fallback ("nếu model không khả dụng → dùng `--entity-provider spacy`") would demonstrate **nothing** about dynamic rules.
- **M5 — Phase-04 E2E commands are invalid click invocations.** `dev sync doc all --project-dir <tmp>` and `dev sync doc all --no-yake --dry-run` (phase-04 steps 1 and 3): `--project-dir/--no-yake/--dry-run` are group-level options (dev.py:3616-3622) and must precede the subcommand. Verified with CliRunner: `["sync","doc","all","--project-dir",...]` → exit 2, `Error: No such option '--project-dir'`. Correct form: `dev sync doc --project-dir <tmp> --no-yake --dry-run all`. As written, steps 1/3 abort before testing anything.
