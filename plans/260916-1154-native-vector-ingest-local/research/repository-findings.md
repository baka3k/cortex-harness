## A. Writer side (cortex-sync native ingest)

### A1. `open_native_store` + the orchestrator call site (what happens on `Unsupported` today)

- `rust/crates/cortex-sync/src/vector_store.rs:28-32` — `pub enum NativeStore { Remote(RemoteQdrantStore), Unsupported(String) }`. There is no local variant; the module doc (:1-14) states the native pass "FAILS CLOSED to `Unsupported`" for every non-remote project.
- `vector_store.rs:101-152` — `open_native_store(qdrant_url: Option<&str>)` decision tree:
  - `CORTEX_STORAGE_PROJECT_ID` set (it IS set for sync runs — `rust/crates/cortex-dev/src/env.rs:470,566`) → hand-rolled registry lookup `registry_backend` (:47-98, merges every `*.json` in `CORTEX_HARNESS_CONFIG_PATH`'s parent dir, casefold match) → `backend == "remote"` + `remote.qdrant_url` → `RemoteQdrantStore::new(...)` (:107-113); remote-without-url (:116-119) and every non-remote backend (:121-126) → `Unsupported`; unregistered project → `Unsupported` (:127-132).
  - No project id: http-shaped `QDRANT_CODE_PATH` → `Unsupported` mirroring Python `RemoteQdrantUnsupportedError` (:140-145); everything else (i.e. a path-shaped locator) → `Unsupported` "local embedded qdrant store … vector lane stays on Python children" (:146-150).
- Call site `rust/crates/cortex-sync/src/orchestrator.rs:2089-2100` (embedding pass, entered when `run_embedding_pass` :2070): on `Unsupported(reason)` it only does `println!("[embedding] native pass unavailable: {reason}")` and sets `native_store = None` (:2095-2098). There is no Python child spawn for vectors anywhere downstream.
- CRITICAL consequence of `native_store = None`: `native_parser = native_store.is_some() && SHARED_VECTOR_CLI_PARSERS.contains(...)` (:2114-2115) is false for every parser, so `finish_native_embedding_pass` (the ONLY vector writer — see A1b) never runs. Phase-08 retired the Python analyzer scripts and the Rust analyzer children explicitly do NOT embed (`rust/crates/analyzer-go/src/goanalyzer.rs:4-5,288-292` hardcodes `vectors=0 vector_status=disabled`; `registry.rs` sets `writes_vectors: false` for the legacy 17). **The local code-vector lane receives ZERO writes today — the pickle store is frozen legacy data.** The summary still stamps `embedding_backend: "python-children"` (:2168, :2348), a stale label since phase-08.
- A1b. The only vector write path: `finish_native_embedding_pass` (`orchestrator.rs:2773-2864`) reads the child's embedding-input artifact → `vector_sync::documents_from_categories` → `vector_store::sync_vector_documents` (:2853). Gate for the pass-level embedder kill-switch: `CORTEX_EMBED_ORCHESTRATOR` in `python|off|0|false|no` disables the whole native pass (:2083-2088).
- What must change to return a local store: add a variant (e.g. `Local(LocalQdrantStore)`) resolved via `cortex_storage::config::resolve_storage` (`rust/crates/cortex-storage/src/config.rs:590`) + `LocalQdrantStore::open(&resolved, "code")` (`rust/crates/cortex-storage/src/qdrant.rs:411`). A ready-made polymorphic seam exists: `cortex_storage::factory::StorageFactory::get_qdrant_store(role) -> QdrantStoreHandle::{Local(LocalQdrantStore), …}` (`rust/crates/cortex-storage/src/factory.rs:346-363`, `QdrantStoreHandle::Local` at :73) — it mirrors the Python `create_storage(targets).get_qdrant_store(CODE)` contract that `local_qdrant.get_code_qdrant_store` implements (`code-tiny/tools/common/local_qdrant.py:68-118`). Note `vector_store.rs` currently deliberately does NOT use the factory (hand-rolls `registry_backend`); reusing `StorageFactory` would also remove that duplication, but changes error/reason strings that phase-06 may pin (check tests, see A2).

### A2. Method-by-method parity: `sync_vector_documents` (`vector_store.rs:267-332`) vs `LocalQdrantStore`

`sync_vector_documents` takes `&RemoteQdrantStore`; store methods used and their local counterparts:

| Remote call (site) | Local equivalent (`rust/crates/cortex-storage/src/qdrant.rs`) | Parity verdict |

| `create_payload_index(collection, field, None)` (:252-259, 4 fields of `SCOPE_INDEX_FIELDS`) | `create_payload_index` (:869-888), same `(name, field, Option<&Value> schema)` shape | Works, but the local engine **appends unconditionally** (:878) — repeated syncs accumulate duplicate `payload_indexes` entries (remote is idempotent server-side, per comment at :250-251). Cosmetic drift; consider dedup on insert |

**Filter-semantics gap (must fix for correctness):** `vector_sync::stale_filter` (`rust/crates/cortex-sync/src/vector_sync.rs:412-451`, byte-pinned by G4 tests :640-661) emits `{"must":[{key, match.value}|{key, match.any}…], "must_not":[{"has_id":[keep_ids]}]}`. The local engine's `point_matches` (`qdrant.rs:280-339`) understands ONLY the `must` array (`key` + `match.value`/`match.any`/`range`); **`must_not` and `has_id` are silently ignored** → a local `delete` with the stale filter would delete the points that should be KEPT (incremental resync of unchanged symbols). Python side has no such gap: `delete_by_filter` passes `qmodels.FilterSelector(normalize_filter(value))` to the real engine which honors `must_not/has_id` (`local_qdrant.py:310-315`). Options: teach `point_matches` `must_not`/`has_id`, or in the local writer path split the delete into filter-delete + id-delete (`points_selector_ids` branch exists :772-785).

Other contract surfaces in `sync_vector_documents` are store-agnostic: scope guard (:279-289), embed + size checks (:290-305), point JSON `{id, vector:f64[], payload}` (:308-318) — the local `upsert` parses exactly this shape (`parse_vector` :208-230, `PointId::parse` :34-44 accepts the uuid string ids).

### A3. `QDRANT_UPSERT_BATCH` + local flush semantics / perf

- `QDRANT_UPSERT_BATCH = 128` (`vector_sync.rs:30`).
- Local persistence: `with_collection(..., persist=true)` calls `client.flush()` **on every mutating op** (`qdrant.rs:427-446`); `upsert`, `create_collection`, `delete`, `create_payload_index`, `set_payload` all persist=true. `flush()` re-serializes the ENTIRE store (all collections, all points) with `write_atomic` (temp+rename) (`qdrant.rs:131-142`; `STORE_FILE_NAME = "cortex-local-store.json"` :25). Read paths (`search`/`scroll`/`retrieve`/`count`) pass `persist=false`.
- Perf risk (inferred from code, not measured): a 9k-point collection × 1024-dim f64 stored as JSON ≈ 20KB/point ≈ ~180MB file; a full parser sync does ~70 upsert calls of 128 → O(n²/batch) re-serialization (multiple GB of JSON formatting per parser per full sync). Two cheap mitigations fit the existing code: (a) accumulate all points of one parser pass and call `upsert` once (one flush per parser — semantics unchanged since every call is durable), and/or (b) add a `persist=false` bulk upsert + explicit `flush` at the end of `sync_vector_documents` (matches the "only last batch waits" durability contract comment at `vector_store.rs:322-323`). `create_payload_index` also flushes per field (4 extra flushes/collection).

### A4. Embedder for `Plane::Code`

- `vector_store::pass_embedder()` = `cortex_embed::embedder_for(Plane::Code)` (`vector_store.rs:375-378`).
- Default backend is **onnx** since the vector-lane phase-02 re-baseline: `rust/crates/cortex-embed/src/backend.rs:2-3,34-44` (`CORTEX_EMBED_BACKEND=python` is the rollback flag; unknown values warn and fall back to onnx). `embedder_for` at backend.rs:108.
- The orchestrator additionally pins the model identity: `embedding_model_name` (`vector_store.rs:364-371`, `--embed-model` → `CODE_EMBEDDING_MODEL` → `jinaai/jina-embeddings-v3`) must equal `cortex_embed::model_for(Plane::Code)` or the pass hard-errors (`orchestrator.rs:2834-2843`). One embedder per pass (`embedder_slot`, :2834-2852) — the 8.3x cold-start win.
- `dev sync code` passes `--embed-model` defaulted from `EMBEDDING_MODEL` env or `jinaai/jina-embeddings-v3` (`rust/crates/cortex-dev/src/cmds/sync.rs:~1015-1022`) — so the model-alignment gate passes as long as `EMBEDDING_MODEL` is unset or jina-v3.

## B. Reader side (cortex-mcp local search, code lane)

### B5. Local-vs-remote decision + sidecar protocol today

- Decision point: `VectorStore` enum + `resolve_store(project_id)` (`rust/crates/cortex-mcp/src/graph/vector_lane.rs:31-54`): registered project with `storage_backend == "remote"` + `remote.qdrant_url` → `Remote{url, api_key}`; **everything else → `Local { store_root }`** and the local arm routes ALL three ops through the Python sidecar:
  - `list_collection_names` → `vector_sidecar::list_collections` (:140-144, sidecar fn at `vector_sidecar.rs:160-175`)
  - `collection_vector_sizes` → `vector_sidecar::collection_vector_sizes` (:162-169, sidecar :178-192)
  - `search_collection` → `vector_sidecar::search_with_using` (:204-207, sidecar :195-230)
- Sidecar protocol: `scripts/rust_mcp/vector_worker.py` — persistent NDJSON stdio, ops `list` / `meta` / `search`, opens `QdrantClient(path=<store>)` (:52-56), search mirrors `qdrant_query_support.search_collection` incl. `PayloadSelectorExclude(["text"])` (:88-96) and optional `using` named vector. Manager: `rust/crates/cortex-mcp/src/vector_sidecar.rs:23-145` — one worker per store path, respawn-once on protocol failure, env `CORTEX_MCP_VECTOR_WORKER` (script path override) + `CORTEX_MCP_PYTHON` (:29-56).
- What must change for the flip: in `vector_lane.rs`, the `VectorStore::Local` arms must call `cortex_storage::qdrant::LocalQdrantStore` instead of `vector_sidecar::*`:
  - `list_collections` → `list_collection_names()` (`qdrant.rs:450-453`)
  - `collection_vector_sizes` → local sizes from `vectors_config` (see A2 gap — `get_collection_info` does not carry sizes; the sidecar's `meta` op read `info.config.params.vectors` from the real client)
  - `search` → `LocalQdrantStore::search(collection, &[f64], limit, filter, with_payload, with_vectors, vector_name)` (`qdrant.rs:559-631`). Note `using`/`vector_name` is supported (`stored_key` :573-580), `with_payload` is boolean only (see B6), and returned hits are `{id, score, payload, vector}` — **no `version` field** (sidecar/QdrantLocal hits carry `version`, `vector_worker.py:100-107`); downstream consumers in `tools_semantic.rs` use only `id/score/payload/_collection`, so `version` absence is likely inert, but the golden fixtures include it (verify comparator tolerance, B10).
- How cortex-mcp resolves the store path: hand-rolled `local_store_root()` (`vector_lane.rs:73-91`): `QDRANT_CODE_PATH` env → else `CORTEX_DATA_HOME`/`$HOME/.cortext-harness` + `v1/instances/<CORTEX_STORAGE_INSTANCE|default>/qdrant/code`. This mirrors `cortex_storage::resolve_storage`'s default derivation (`config.rs:691-721`, `ENV_QDRANT_CODE`/`ENV_INSTANCE` consts at :22-28) and passes the layout parity test (`cortex-storage/tests/parity.rs:186`), but it does NOT honor config-file `qdrant_code_path` keys, the `QDRANT_PATH` base override, or `CORTEX_CODE_STORAGE_OWNER` owner names. For the flip, prefer calling `cortex_storage::config::resolve_storage` + `LocalQdrantStore::open(&resolved, "code")` so both sides share one resolver (mind lane already uses the same hand-rolled chain for doc: `rust/crates/cortex-mcp/src/mind/qdrant.rs:72-97,110-131`).
- Tools that consume the lane (unchanged by the flip): `graph/tools_semantic.rs:345-471` (`semantic_search`: resolve → embed → list → `filter_collections_for_vector` :393-422 → per-collection `search_collection` + `_collection` tag :449-470 → `merge_hits` :471 → `_select_content` + prune :474-495) and `graph/tools_explore.rs:1203-1254` (`explore_graph` qdrant seeds).

### B6. Search-semantics parity: Python ground truth vs `LocalQdrantStore::search`

Python reference (`code-tiny/tools/common/qdrant_query_support.py`):
- filter `project_id_normalized match.any` prefix-expansion — already mirrored natively in `vector_lane::project_scope_filter` (`vector_lane.rs:267-287`), emits `{"must":[{"key":"project_id_normalized","match":{"any":keys}}]}`.
- `merge_hits` dedupe by `str(id)` keep-higher-score, stable sort desc, cut top_k — mirrored in `vector_lane::merge_hits` (:291-335).
- `PayloadSelectorExclude(["text"])` (:35, `search_collection` :77) — the sidecar reproduces it (`vector_worker.py:93`); **`LocalQdrantStore::search` has no payload selector — `with_payload` is bool** (`qdrant.rs:559-568`): either post-strip `"text"` from returned payloads in `vector_lane.rs` (exact parity, cheap — text is the only excluded key) or extend the local engine (more invasive). Note `tools_semantic.rs:489-493` prunes `summary/comment/code/note/text` post-merge when `!include_raw_fields`, which masks much of the difference but not for `include_raw_fields` runs and not for the payload bytes crossing `merge_hits`.
- `QDRANT_HNSW_EF` query param (`qdrant_query_support.py:41-49,69-71`) — no HNSW in either local engine; the sidecar already ignores it (not passed, `vector_worker.py:85-96`); `LocalQdrantStore::search` has no search_params either. No action needed for parity-vs-sidecar (documented divergence for local mode).
- Local engine filter support (`qdrant.rs:280-339`): `must` with `key` (dotted-path), `match.value`, `match.any`, `range` — **sufficient for `project_scope_filter`**; `should`/`must_not`/`has_id` unsupported (matters for the writer delete, A2; the reader filter never uses them).

Scores:
- `LocalClient` stores vectors as parsed **f64** (`as_f64`, `qdrant.rs:208-230`) and computes `dot/(‖a‖·‖b‖)` in f64 (`cosine_score` :245-258, non-mutating).
- QdrantLocal (`qdrant-client` embedded, sidecar path) stores vectors as **np.float32** arrays and computes cosine by in-place-normalizing then `np.dot` (verified in `.venv/lib/python3*/site-packages/qdrant_client/local/distances.py:121-141` — `vectors /= norm`, and `local_collection.py:121,239,265` `dtype=np.float32`).
- **Exact float equality is NOT expected** (f32 storage rounding + normalized-dot vs ratio formula ≈ 1e-7…1e-6 relative differences) — inferred from the numpy code above; the existing comparator tolerance (1e-6 absolute, B10) is the right instrument, but this must be proven with a real fixture before flipping, not assumed. Tie-order: QdrantLocal sorts via `np.argsort` (local_collection.py:668-670, not stable ⇒ tie order unspecified); LocalClient breaks score ties by point-id sort key (`qdrant.rs:592-604`). Ties are rare with real embeddings (inferred).

## C. Data / re-index / detection

### C8. Path resolution on both sides + full re-sync command

- Python writer/reader resolution: `local_qdrant.get_code_qdrant_store` (`code-tiny/tools/common/local_qdrant.py:68-118`) → `StorageFactory` via `cortex_harness.storage.resolve_storage` (project_id branch) or `resolve_storage(root, qdrant_code_path=QDRANT_CODE_PATH)` fallback (:47-59,115-118).
- Rust writer-side resolution: `cortex_storage::config::resolve_storage` (`config.rs:590-802`); precedence CLI overrides > config file > env > derived default (`data_root/v1/instances/<instance>/qdrant/<owner>`, :691-721). In `dev sync code` runs the child env always carries the resolved absolute `QDRANT_CODE_PATH` via `storage_overlay` (`config.rs:830` for local; overwritten with the URL for remote :869) plus `CORTEX_STORAGE_PROJECT_ID` (`cortex-dev/src/env.rs:470,566`).
- Rust reader (cortex-mcp): hand-rolled `local_store_root()` (`vector_lane.rs:73-91`) — same default path, fewer override keys (see B5). Recommend unifying on `resolve_storage`.
- Legacy-store detection point: the legacy qdrant-client layout on disk is `<store_root>/collection/<name>/storage.sqlite` + `meta.json` + `.lock` (verified live under `~/.cortext-harness/v1/instances/default/qdrant/code/`); the Rust JSON engine writes `<store_root>/cortex-local-store.json` (`qdrant.rs:25`, flushed :131-142) and `LocalClient::open` `create_dir_all`s an absent dir (:106-108). A natural detection helper: "store dir contains `collection/` (or any `storage.sqlite`) and no `cortex-local-store.json`" → refuse/fail-closed with a re-index instruction. Best homes: next to `LocalClient::open`/`LocalQdrantStore::open` (defensive, protects both writer and reader) and/or in the new `open_native_store` local branch.
- Full re-sync commands that exist today:
  - `dev sync code <folders> --full-scan` → cortex-sync `--full-scan` (`cortex-dev/src/cmds/sync.rs:814,912-913`).
  - Embedding-only full pass: `--sync-mode embedding --full-scan` (validated `cli.rs:396-404`; requires qdrant configured — satisfied locally by the overlay-exported `QDRANT_CODE_PATH`). Full scan forces the non-incremental path (`orchestrator.rs:2214`: `run_incrementally = incremental_supported && (!full_scan || recovery)`), and the embedding artifact's `full_replace` flag then drives `stale_filter(full_replace=true)` (`vector_sync.rs:428-441`) → deletes the whole scope before re-upsert. Since the store starts empty after the delete+recreate, a per-instance recipe is: stop MCP (lease, see C9), delete `<store_root>`, `dev sync code --full-scan` (or `--sync-mode embedding --full-scan` after a graph sync) — no `--force` flag exists.

### C9. Is deleting the old store safe?

- Nobody parses `storage.sqlite` outside qdrant-client: `qdrant_layout_cache.py` and `incremental_cleanup.py` go through `get_code_qdrant_store` store APIs only (`code-tiny/tools/common/qdrant_layout_cache.py:22,47-52`; `incremental_cleanup.py:5,139`); grep found no other direct reader. On a deleted store these either find no collections (cleanup: "collection not found; skip", `incremental_cleanup.py:142`) or report empty lists.
- Filename collision: none — legacy writes `collection/<name>/storage.sqlite`; Rust writes `cortex-local-store.json` at the same dir root (C8). A stale legacy tree can coexist with a fresh JSON store in one directory, which argues for physically removing the legacy dir (or at least the detection guard) rather than leaving both.
- **Lease contention (the big operational catch):** `LocalQdrantStore::open` → `get_client` acquires an EXCLUSIVE `flock` lease `.cortex-owner.lock` beside the store and caches it for process lifetime (`qdrant.rs:358-393` cache holds `StorageLease`; acquire is `LOCK_EX|LOCK_NB`, `lease.rs:79-131`, conflict message "Embedded qdrant store is already owned… Stop that owner process"). The sidecar does NOT take this lease, which is why today's Python-writer + Rust-reader coexistence works. After the flip both writer (cortex-sync) and reader (long-lived cortex-mcp server) would want the same lease → **whoever opens second hard-fails**. The Python wrapper has the same behavior (`cortex_harness/storage/qdrant.py:41-67,367-380` — lease released on `close()`), and `LocalQdrantStore::close` exists (`qdrant.rs:894-901`) but only drops the cache entry per role. The plan must pick a strategy: e.g. reader opens/closes per request burst, writer holds the lease only during the sync run with MCP stopped, or a short-lived-lease mode in `get_client`. This is a design decision, not just an implementation detail — flag it in the plan.

## Risks / open questions

1. **Lease contention writer-vs-reader (HIGH, verified):** exclusive flock per store path held for process lifetime by `LocalQdrantStore` (`qdrant.rs:358-393`, `lease.rs:79-131`) — flipped reader (long-lived MCP) + native writer (sync) cannot both hold it. Strategy undecided: per-request open/close in MCP vs lease-only-during-sync vs a shared short-lease mode. Unknown: whether qdrant-client's internal `.lock` (legacy store only) also blocked concurrent Python writer + sidecar reader in practice (sidecar ignores the cortex lease; never observed failing — inferred benign).
2. **`must_not`/`has_id` delete gap (HIGH, verified):** local `point_matches` ignores `must_not` (`qdrant.rs:280-339`) while `stale_filter` always emits it for incremental syncs (`vector_sync.rs:444-449`) → local deletes would eat kept points unless the engine or the call path is fixed.
3. **`vector_sizes` shape mismatch (verified):** local `get_collection_info` carries no vector config (`qdrant.rs:462-478`) → drift guard silently no-ops; needs a parallel parser (decision open: extend info shape vs dedicated method).
4. **Flush-per-op O(n²) serialization (verified mechanism, magnitude inferred):** full-store JSON rewrite per mutating op (`qdrant.rs:131-142,427-446`); ~8-9k-point collections × 70 batches → likely minutes of serialization per parser full sync unless upsert is coalesced (A3).
5. **Score parity f64-vs-float32 (inferred):** QdrantLocal stores np.float32 and normalizes before dot (`distances.py:121-141`); LocalClient is pure f64 ratio (`qdrant.rs:245-258`). Expect ≲1e-6 diffs — must be fixture-proven, not assumed; tie-break order also differs (unstably sorted numpy vs id-key, B6).
6. **`version` field + payload exclusion shape (verified absence):** local search hits lack `version` and can't exclude `text` server-side; golden fixtures contain `version`; `include_raw_fields` runs would leak `text` unless post-stripped (B5/B6).
7. **Local lane currently receives no writes (verified):** post-phase-08, `native_store = None` on local means zero vector writes (A1) — so "existing pickle data" is stale by definition; re-index is not only format migration but a data refresh. Unknown: how stale real user instances are (not measurable from repo).
8. **Legacy detection key:** task text says "storage.sqlite presence"; actual on-disk legacy layout is `<root>/collection/<name>/storage.sqlite` + `meta.json` (verified live). Detection should key on the `collection/` dir to be version-robust (older qdrant-clients used a single `storage.sqlite` at root — unverified/inferred).
9. **Duplicate `payload_indexes` accumulation on local (verified mechanism, impact cosmetic):** repeated `create_payload_index` appends (`qdrant.rs:877-884`).
10. **Open question:** whether `open_native_store` should switch to `StorageFactory::get_qdrant_store` (removes hand-rolled registry, gives `Local` for free) or keep the hand-rolled branch to preserve exact reason strings pinned by phase-06 tests — needs a test audit before choosing (A1).
